# 설계 변경: 프로젝트 진행 상태를 서버에 저장 ("이어서 하기")

- 브랜치: `feat/server-progress` (acc-backend, acc-front, acc-deploy)
- 계기: [TROUBLESHOOTING #10](TROUBLESHOOTING.md#10-파생-만들기가-존재하지-않는-프로젝트에-저장--400) — 파생 만들기가 존재하지 않는 프로젝트에 저장된 문제

## 1. 배경

ACC 의 홍보물 제작은 여러 화면에 걸친 긴 흐름이다.

```
/select 유형 선택 → /upload 기획서 업로드 → /proposalloading 분석(프로젝트 생성)
 → /analyze/* 분석 결과 → /generate-prompt/loading 생성
 → /create/poster|mascort/detail 베이스 선택 → /create/upload → /testlodingpage → /editorpage
```

생성 한 번에 수 분이 걸리고 외부 API 비용이 든다. 그래서 **중단되거나 실패해도 이전 단계를 기억하는 것**이 원래 목표였다.

## 2. 이전 설계: 브라우저 sessionStorage

화면 사이에 넘기는 값 21개를 각 화면이 직접 `sessionStorage` 에 쓰고 읽었다.

| 구분 | 키 | 서버 DB 에도 있나 |
|---|---|---|
| 프로젝트·기획서 | `proposalData`, `editorPNo` | O (project, proposal_metadata) |
| 생성 결과 | `posterThumbnailList`, `mascotThumbnailList`, `generatedImages`, `posterPromptList`, … | O (prompt, generated_asset) |
| 분석 결과 | `trendData`, `regionTrendData`, `bannerTrendData` | X |
| 사용자 선택 | `types`, `selectedPosterImage`, `selectedMascotImage`, `uploaded*Image` | X |

```
화면 A ──setItem──▶ sessionStorage ──getItem──▶ 화면 B        (서버는 모름)
```

### 문제

1. **같은 탭 안에서만 유효하다.** 탭을 닫거나 다른 기기에서는 이어갈 수 없다.
2. **이중 저장이다.** DB 에 있는 값을 복사해 두고 따로 고친다. 한쪽만 바뀌면 어긋난다.
3. **덮어쓰기에 취약하다.** 분석 결과 화면이 `proposalData` 를 입력값만으로 덮어써 `pNo` 가 사라졌고, 그 뒤 화면들이 `|| 1`, `|| 18` 같은 임의 번호로 대체해 **엉뚱한 프로젝트에 저장**했다.
4. **서버가 클라이언트의 pNo 를 그대로 믿었다.** 위 문제가 보안 문제(남의 프로젝트에 저장)로도 이어졌다.
5. **"어디까지 했는지"를 알 수 없다.** 마지막 화면 정보가 없어 이어서 하기를 만들 수 없었다.

## 3. 바뀐 설계: 서버가 진행 상태의 원본

```
            ┌───────────── ProjectGate (진입 시 서버에서 불러옴, 현재 경로 기록) ─────────────┐
화면 A ──projectSession.setItem──▶ projectStore ──(400ms 모아서 PUT)──▶ /api/progress/{pNo} ──▶ project_progress
화면 B ◀──projectSession.getItem── projectStore ◀────────(GET)──────────────────────────────────┘
브라우저에는 "지금 보는 프로젝트 번호(pNo)"만 남는다
```

### 3.1 DB — `V4__project_progress.sql`

| 컬럼 | 설명 |
|---|---|
| `p_no` (PK, FK → project, ON DELETE CASCADE) | 프로젝트 |
| `m_no` | 소유 회원 (조회 인덱스) |
| `route` | 마지막으로 머문 화면 경로 → "이어서 하기"가 돌아갈 곳 |
| `state` (MEDIUMTEXT, JSON) | 화면 간 공유 값. `키 → JSON 문자열` 맵 |
| `updated_at` | 최근 프로젝트 판단 기준 |

### 3.2 API — `/api/progress`

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/current` | 가장 최근에 진행한 프로젝트. 기록이 없으면 최신 프로젝트, 프로젝트가 없으면 204 |
| GET | `/{pNo}` | 특정 프로젝트. 기록이 없으면 DB 의 기획서 정보로 시작 상태를 만든다 (기존 프로젝트 호환) |
| PUT | `/{pNo}` | `{ set: {키: 값}, remove: [키], route }` 를 기존 상태에 병합 |

모두 `ProjectAccess.check(pNo)` 로 **본인 프로젝트만** 다룬다 (없음 404 / 남의 것 403 / 관리자 허용). 같은 검사를 `pNo` 를 받는 에디터 API(`save-image`, `build`, `template-json`)에도 적용했다.

### 3.3 프론트

| 구성 요소 | 역할 |
|---|---|
| `store/projectStore.js` (Zustand) | 서버 상태의 사본. 쓰기는 즉시 반영하고 서버에는 400ms 모아서 PUT. 실패하면 다음 저장에 다시 보낸다. 탭을 닫을 때는 `fetch(keepalive)` 로 남은 변경을 보낸다. 브라우저에는 `pNo` 만 저장 |
| `utils/projectSession.js` | `sessionStorage` 와 **같은 사용법**(`getItem`/`setItem`/`removeItem`, 동기) |
| `components/project/ProjectGate.jsx` | 흐름 화면의 입구. `?p=` → 이 탭의 프로젝트 → 최근 프로젝트 순으로 불러온 뒤 화면을 그린다. 현재 경로를 `route` 로 기록 |
| `utils/project.js` `openProject(pNo?)` | 이어서 하기: 프로젝트를 열고 마지막 화면 경로를 돌려준다 |

이어서 하기 진입점:
- **메인 화면**: "이어서 하기 · 2023 태화강 국가정원 봄꽃축제 (포스터 선택)" → 가장 최근 프로젝트
- **마이페이지 → 프로젝트 상세**: "이 프로젝트 이어서 하기" → 고른 프로젝트
- 주소로 직접: `/analyze/list?p=4`

## 4. 설계 결정과 이유

### 화면을 다시 짜지 않고 저장소만 바꿔 끼웠다 (`projectSession`)
- 16개 화면에서 89곳이 sessionStorage 를 썼다. 화면마다 서버 API 호출로 다시 쓰면 변경량과 회귀 위험이 크다.
- 그래서 `sessionStorage` 와 같은 **동기 인터페이스**를 유지하고, 저장 위치만 서버로 옮겼다. 화면 로직은 그대로라 기존 동작과 같다.
- 동기 조회가 가능한 이유는 `ProjectGate` 가 화면을 그리기 **전에** 서버 상태를 불러오기 때문이다.

### 상태를 정규화된 컬럼이 아니라 JSON 맵으로 저장했다
- 화면마다 넘기는 값의 모양이 다양하고 자주 바뀐다. 컬럼으로 정규화하면 화면 하나 바꿀 때마다 마이그레이션이 필요하다.
- 진행 상태는 "작업 중 임시값"이라 검색·집계 대상이 아니다. 확정된 결과(기획서, 프롬프트, 생성 이미지)는 기존처럼 정규화된 테이블에 있다.
- 대신 **기획서 정보는 DB 가 원본**이다. 진행 기록이 없으면 `proposal_metadata` 에서 채운다.

### 쓰기는 모아서(디바운스) 보낸다
- 유형 선택처럼 클릭마다 값이 바뀌는 화면이 있다. 매번 PUT 하면 요청이 많다.
- 화면 간 이동은 스토어(메모리)에서 즉시 읽으므로, 서버 저장이 400ms 늦어도 흐름에 영향이 없다.
- 탭을 닫는 순간의 유실은 `pagehide` + `keepalive` 로 막는다.

### "이어서 하기"는 단계 코드가 아니라 마지막 화면 경로로 기록한다
- 단계 코드(enum)를 따로 두면 화면 구조와 이중 관리가 된다. 경로는 화면 자체라 어긋나지 않는다.
- 들어가면 작업이 다시 실행되는 진행 화면(`/proposalloading`, `/generate-prompt/loading`, `/testlodingpage`)은 기록하지 않는다. 그래서 이어서 하기는 그 직전 화면으로 돌아간다.

### 유형 선택(`/select`)은 초안으로 둔다
- 유형 선택은 기획서 분석(= 프로젝트 생성) **전** 단계다. 아직 저장할 프로젝트가 없다.
- 그래서 이 탭의 sessionStorage 에 초안으로 두고, 분석이 끝나 프로젝트가 생기는 순간 서버 상태로 옮긴다.

### 기존 데이터 호환
- 이 변경 전에 만든 프로젝트는 진행 기록이 없다. `GET /{pNo}` 는 기록이 없으면 DB 기획서 정보로 시작 상태를 만들어 `/analyze/list` 에서 시작한다.
- 마이그레이션(V4)은 테이블 추가만 하므로 기존 테이블과 데이터에 영향이 없다.

## 5. 이전과 비교

| | 이전 (sessionStorage) | 이후 (서버 진행 상태) |
|---|---|---|
| 새로고침 | 유지 | 유지 |
| 탭 닫고 다시 열기 | **유실** | 이어서 하기 |
| 다른 기기·브라우저 | 불가 | 이어서 하기 |
| 여러 프로젝트 중 골라 이어가기 | 불가 | 마이페이지에서 가능 |
| 프로젝트 번호 | 화면마다 복사, 없으면 `\|\| 1`, `\|\| 18` | 현재 프로젝트 하나, 없으면 중단 |
| 남의 프로젝트 번호로 저장 | 가능 | 403 |
| 저장 위치 | 21개 키, 16개 화면에 분산 | `project_progress` 1행, 접근 경로 1개 |

## 6. 검증

API (로컬 Docker, nginx 경유):

| 시나리오 | 결과 |
|---|---|
| 진행 기록이 없는 기존 프로젝트를 최근 프로젝트로 조회 | 200, DB 기획서 정보로 시작 상태, `/analyze/list` |
| 저장 → 재조회 → 키 삭제 | 정상 반영 |
| 프로젝트가 없는 새 회원의 최근 프로젝트 | 204 |
| 다른 회원이 조회·저장·이미지 저장·템플릿·빌드 | 모두 403 |
| 관리자 조회 | 200 |
| 없는 프로젝트 / 토큰 없음 | 404 / 401 |

화면 (수동 확인 항목):
- [ ] 새 기획서 분석 → 분석 결과 → 생성 → 베이스 선택 → 에디터까지 기존과 같이 진행
- [ ] 중간 단계에서 탭을 닫고 메인에서 "이어서 하기" → 같은 단계로 복귀
- [ ] 마이페이지에서 다른 프로젝트를 골라 "이어서 하기" → 해당 프로젝트로 전환
- [ ] 로그아웃 후 다른 계정으로 로그인 → 이전 계정의 프로젝트가 보이지 않음

## 7. 다음 단계

같은 진행 상태 테이블 위에 **백그라운드 생성 작업**을 얹는다. 생성 요청은 즉시 "접수"로 응답하고, 진행률("마스코트 3/4")과 예상 시간을 기록한다. 사용자는 다른 화면으로 가도 되고, 돌아오면 이어서 본다.
